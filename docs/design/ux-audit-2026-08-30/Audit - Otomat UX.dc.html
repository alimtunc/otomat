Otomat — UX/UI audit
o Otomat · UX/UI audit & redesign plan · August 26, 2026 · read-only session — no source modified

Quieter chrome, louder state

Otomat’s bones are excellent: a real design-token system, a central status registry, honest event-sourced data, resizable instrument panes. The problems are almost all semantic — the wrong hue on live state, chrome that repeats itself, terminal states that keep dead controls on screen, and machine vocabulary leaking into reading surfaces. Every recommendation below reuses the existing token and component system.

Redesign board → 6 screens Flow storyboards → 3 flows Current-state recreations → 6 screens Implementation prompt → 3 batches, ready to send

Method & evidence

26 screenshots (primary visual evidence) + full read of the relevant source: packages/ui (tokens, primitives, status registry), the web shell (route-shell, sidebar, topbar), and the priority views (runs list, run cockpit, conversation, PR, usage, issue detail, settings/workspaces, inbox, reviews). The live app was not exercised. Every finding is tagged:

shot — visible in a screenshot src — proven in source code verify — needs a screenshot or live test

Keep — what already works

  • One status registry. ui/lib/status/registry.ts maps every state of 12 domains to tone + icon + label. Nothing else in the codebase invents status colors. This is the lever that makes the P0 color fix a one-file change.
  • Token discipline. tokens.css covers surfaces, status, provenance, spacing, motion, density and even live theme identities (brass/viridian). Values are tunable by contract.
  • State coverage. Skeletons, error states with retry, empty states with actions, offline banner, reconnecting bar, stale-data notice all exist as shared components — the audit found no missing state class, only uneven use.
  • Instrument layout. Resizable, collapsible panes with persisted layout; command palette; consistent focus rings; labeled icon buttons.
  • Evidence-first copy. “Nothing is estimated”, deterministic reports, permission requests recorded in the ledger — the product’s honesty is a differentiator. The redesign keeps it and only changes where the honesty is spoken.

Prioritized findings

P0 1 · The live/interactive/danger hue collision fix → 1a

A1. --iris-solid #f0645a is perceptually identical to --danger #f2545b. The design doc (§1) built the system around a blue iris (#5B7CFA) carrying “primary action, focus, selection and the live/running state”; when the brand hue moved to coral, every live/selected state started reading as failure. Symptoms across the screenshots: “Active” worktrees look alarming in Settings › Workspaces, the selected step in the cockpit sits on a red wash, the sidebar “live run” dot reads as an error, “Ready” issues look flagged. shot src: tokens.css · docs/design/otomat-v1-design-system.md

A2. The same word gets two colors: a workspace “Active” is iris (lib/workspace/state.ts) while a session “Active” is success-green (registry.ts). src

Fix. Introduce --live (a blue, e.g. #4da3ff) + --live-bg; remap only motion states — run/step running·preparing·starting, contribution sending, compete promoting, workspace active — to the live tone. Coral stays for primary actions, selection and focus. One tone added in tone.ts, ~10 lines changed in registry.ts, zero component changes.

P0 2 · Chrome repeats itself; Settings is hidden fix → 1a

B1. Settings has no persistent navigation entry — it is reachable only through the project-switcher popover or the palette. The source states it: project-switcher.tsx — “the switcher is the only way in, so it is required”. For an alpha whose setup lives in Settings (hosts, repositories, integrations), that is a daily tax. shot 01.05.48 src

B2. Up to five stacked chrome rows before content, three of which repeat the project identity: the tab strip pill (“otomat supervps”), the switcher (“otomat supervps · otomat”), and the topbar label (“otomat”), then a 48px page header, then a 42px toolbar. ≈176px of chrome above the first data row on list views. shot 01.05.23, 01.03.21 src: route-shell.tsx, app-shell.tsx, topbar.tsx

B3. Two search affordances for one command: the sidebar “Search ⌘K” item and the 230px topbar search button both open the palette. src: sidebar.tsx + route-shell.tsx

B4. Cockpit tabs (Conversation·Report·Logs·Diff·PR) sit in the right-hand “actions” slot, detached from the run they describe, and collapse to unlabeled icons below lg. src: cockpit/tabs.tsx verify narrow width

Fix. One 48px PageBar (breadcrumb/title + status + view actions + activity + connection) replaces topbar + page header; the topbar search button is removed (sidebar item + ⌘K remain); Settings becomes a pinned sidebar footer item; cockpit tabs center in the PageBar. Keyboard behavior unchanged.

P0 3 · Terminal states keep dead controls alive fix → 1b · 1c

C1 — the PR tab after merge (your named pain point) encodes one fact four conflicting ways: a purple “merged” banner, a danger-red notice (“Pull request #183 is merged; it takes no further publication.”), a fully-filled progress stepper, and — below all that — a complete, editable-looking form (Type/Scope/Summary/Description/Branch/Publication) with an AI-generate button and a disabled primary. Meanwhile the summary reports “no workspace · no GitHub remote · 0 files · +0 −0” because the worktree was cleaned post-merge — data honesty reading as breakage. shot 01.05.23/28 src: pr/view.tsx renders PullRequestForm unconditionally; summary.tsx

C2. A finished run keeps a full composer — textarea plus an enabled-styled coral “Send message ⌘↵” — directly above the caption “This run is finished — its session can no longer be resumed.” shot 01.04.27 src: conversation/composer.tsx (gate note vs. button state)

C3. No surface answers “what now?”. After review_ready or completed, the next step (review diff → publish → open PR) hides in a right-rail button row; the runs list offers nothing inline for waiting runs. shot src: cockpit/run/action-buttons.tsx

C4. The Report tab stamps EVIDENCE ten times on one screen and triple-encodes the hero (“Succeeded” + completed chip + EVIDENCE). shot 01.04.36

Fix. A pure resolveNextAction(detail, pr, review) in web/lib/run/ drives: a next-action strip in the cockpit, the lead card in the run-context rail, inline actions on waiting rows in the runs list, and a state-driven PR tab — terminal states render an outcome card (facts that survive cleanup + the Linear consequence + a read-only “Publication details” disclosure) and never an editable form. Merged is review-purple or success — never danger. Composer swaps for a closure bar on terminal runs.

P1 4 · Numbers speak machine, not operator fix → 1d

D1. Token counts always render in “k”: 5353947k, 33386k, 110794k — unparseable at a glance and the top complaint driver on the Usage view (your named pain point). shot 01.03.02 src: web/lib/run/usage.ts formatTokenCount

D2. Costs carry 3 decimals and no thousands separator ($6279.101); PARTIAL/FINAL shout in caps with no explanation anywhere. shot

D3. The daily chart has no y-scale, no hover values, first/last date only; the “By project” meter is invisible at 1 project (fill = 12%-alpha coral on a dark track); the per-run Tokens cell stacks a 2×2 grid into a 44px row. shot src: daily-chart.tsx, breakdown.tsx, cells/tokens.tsx

Fix. Tiered units (k/M/B) with the exact value on hover/copy; $#,##0.00; “partial” becomes an info glyph + sentence (“2 runs did not report cost”); “FINAL” disappears — final is the default, only live counting gets a marker. Chart: metric toggle (Tokens/Cost/Runs), two dashed gridlines with labels, weekly ticks, hover tooltip. Breakdowns get share-% and a solid 4px meter. One formatting module feeds usage, steps pane, run facts and runs list.

P1 5 · Repetition where a signal should be fix → 1e · 1f

E1 — Workspaces (your named pain point): the same full state sentence repeats under every row (“The issue is still working here — merge or abandon its cycle first.” ×5, “No merged canonical pull request…” ×7 in one screenshot), doubling row height and burying the actual variance (which repo, which branch, dirty or clean). Zero-count filter chips (Stale 0, Missing 0) still render; cleanup has no bulk action although the count is right there. shot 01.08.32 src: workspaces/section.tsx, cells

E2 — Issue detail (your named pain point): the issue’s status appears four times in two vocabularies — header chip “ready”, meta “Todo”, rail Properties “ready”, rail Linear “Todo” — and the primary action (“Launch run”) sits both top-right and below the full spec, so on a long issue the empty-state launcher is one full page-scroll away. The PR-attach input renders prominently even when no PR exists. shot 01.04.07/16 src: detail-view.tsx, workspace-rail.tsx

E3 — Steps pane: three identical “claude · terminated · Context” rows per step, plus a mono usage line, push the actual step list off-balance. shot 01.04.27 src: steps/row.tsx

Fix. State sentences → tooltip on the chip (a legend row exists once, not per row); one-line 40px workspace rows with hover actions; “Clean up N” bulk strip; zero-count chips collapse behind “+N empty states”. Issue detail: one status control with the sync consequence written under it; a compact launcher row above the fold; the spec clamps at ~300px with “Show full spec”. Sessions collapse to “N sessions · terminated”.

P1 6 · Machine vocabulary on reading surfaces fix → 1b

F1. The conversation — the main reading surface — speaks in event types: “ordered by seq”, “run review_ready”, “Otomat · run.lifecycle”, “report v1 · deterministic”; the run header packs five provenance facts into one unbroken line (“finished Reviewer · Claude Code claude-fable-5 · high Requested: fable · Reported: claude-fable-5 … fable”). shot 01.04.27, 01.04.36 src: conversation/view.tsx, timeline/event-summary

F2. Provenance dots (coral = Otomat) are color-only — the one place the design system’s own “status is never color-only” rule is broken. src: design-system.md §0 vs. ledger rows

Fix. A sentence template per event type (“Run is ready for review”, “Turn completed”) with the raw type + seq in the expanded detail and tooltips; the header becomes “Reviewer · Claude Code — fable-5 · high effort” + a mono session id; “ordered by seq · live” becomes a live pill with a tooltip. No data is removed — it moves one level down.

P1 7 · Duplication the shared layer should absorb

G1. components/inbox/* and components/reviews/* are parallel implementations of the same pattern — entry-row, filters-menu, empty-state, group-section — differing only in grouping and tone. src: file tree

G2. Shell-grade pieces live app-side and get re-invented: PaneHeader (runs), SectionHeading (settings), CenteredState, list skeletons. Promote to packages/ui.

G3. Three menu-configuration systems coexist: config-menu, the execution submenus, and issues view-options. Converge on config-menu.

G4. Settings pages surface 3–5 coral primaries at once (Save init commands, Map source, Apply, Save defaults…). Primary should be dirty-state-gated, one per card, default variant otherwise. shot 01.07.58, 01.08.37, 01.08.54

P1 8 · Readability floors

H1. 10px and 9px text carries real information: step participant lines (text-[10px] in steps/row.tsx), session status, FINAL/PARTIAL tags. Floor is 11px in the product’s own type scale. src

H2. --text-tertiary #646a76 on #0a0b0d ≈ 4.0:1, used at 11–12px for timestamps, notes, axis labels — below the design system’s own “secondary ≥ 4.5:1” contract. Raise the token (≈#7a8291) or reserve tertiary for decorative text. src: tokens.css vs design-system.md §1 verify with axe

H3. Lowercase status labels (“awaiting permission”) in a mixed FR/EN interface slow scanning; worth an A/B in the gallery before changing — it is an identity choice. verify

P2 9 · Motion & perceived responsiveness behavior → flows

I1. Motion tokens exist (--motion-*, --ease, reduced-motion path) but state changes are hard cuts: chips flip, ledger rows pop, counts jump. Proposed: 140ms tone/label crossfade on chips, fade+2px rise for new ledger rows (batched per frame under streaming), count-up ≤300ms on usage tiles. src: tokens present, few usages verify live feel

I2. Launch feels modal-bound: the dialog stays until the daemon answers. Proposed optimistic handoff — navigate to the cockpit ≤200ms with a “preparing” live chip and skeleton thread (the run row already exists in the ledger). verify current latency

Implementation batches — medium (3–5 days each)

1State colors & number languagefoundation · lowest risk · widest spread

Scope. --live token + tone facets; registry remap (run/step/compete/contribution motion states); workspace/state.ts active→live; tiered formatTokenCount + formatCostUsd and their call sites (usage tiles/cells, steps pane, run facts, PR summary); PARTIAL→info-glyph component with sentence; drop FINAL; kill 9–10px text in runs components; raise --text-tertiary.

Acceptance. No running/active/selected state renders in the #f0645a…#f2545b band; Workspaces counter “Active” is blue; every token count in the app renders ≤4 significant characters + unit with the exact value on title; costs show 2 decimals + separators; no informational text below 11px in components/runs/**; chip text contrast ≥4.5:1.

Validation. Unit: registry tone snapshot + formatter table tests. Visual: gallery pages (apps/web/src/gallery) before/after screenshots; axe pass on gallery; rg "text-\[(9|10)px\]" apps/web/src/components/runs returns nothing; pnpm check green.

2Terminal states & next action (run surfaces)the two named pain points on runs

Scope. resolveNextAction resolver + tests; cockpit next-action strip + rail lead card; composer→closure bar on terminal runs; PR tab state-driven layout: terminal = OutcomeCard (surviving facts + Linear consequence + read-only publication disclosure + “workspace cleaned” reframe), pre-publish keeps today’s form; Report EVIDENCE de-duplication (one explainer + subtle per-card tag); runs list inline “Answer” / “Follow live” affordances on waiting/running rows.

Acceptance. For each of {completed+merged, completed+unpublished, review_ready, failed, canceled, awaiting_permission}: exactly one primary next action across cockpit + PR tab; post-merge shows zero editable fields, zero AI-generate, zero danger tone; composer textarea absent on terminal runs and replaced by the closure bar; existing publish/generate behavior unchanged pre-publish (contract tests untouched).

Validation. Drive each state with the deterministic fake runtime adapter (apps/local-daemon/src/runtime) and snapshot the three surfaces per state; resolver unit tests cover every RunState; manual pass on a real merged run (this repo has OTO-139 · #183).

3Chrome merge & list grammarshell + workspaces + inbox unification

Scope. PageBar merge in route-shell (drop topbar search field + project label; keep ⌘K, sidebar Search, palette); Settings sidebar entry; cockpit tabs centered; Workspaces one-line rows + chip tooltip + “Clean up N” bulk (loops the existing per-workspace delete; confirm dialog lists branches) + zero-count chip collapse; shared InboxRow/Group adopted by Inbox and Reviews; runs-list row upgrade (outcome summary + cost from the usage rollup — needs check: steps/cost per run on the list endpoint; if absent, render from the run-detail cache and add a daemon aggregate later).

Acceptance. ≤2 fixed bars above content on list views (≤96px, was ≈176px); Settings reachable in one click from every view; project identity rendered once in the chrome; workspace rows are 40px single-line, sentences appear on hover, bulk delete touches only cleanup_required; Inbox and Reviews render through the same row/group components; no keyboard regression ([, ⌘K, C, tab shortcuts).

Validation. Keyboard smoke script; 1180px-width pass (tabs collapse gracefully, PageBar truncates breadcrumb not actions); import-boundary lint (pnpm build) confirms no app→app leaks from the shared rows; pixel review of gallery + the six recreated screens vs. redesign boards; pnpm check green.
